# Enact move tests

Test data and acceptance definitions for moving this kit's agents onto Enact
([prismteam-ai/enact](https://github.com/prismteam-ai/enact)). Agent packages live in
`enact/<agent>/` and are generated by `scripts/sync-enact-agents.mjs`. This folder holds only
the tests.

```text
enact/tests/
├── plan.json                      # stays-local agents, waves 1a/1b, gates
├── golden/<agent>.json            # 2-3 golden tasks for every Enact-hosted agent (T3, T4)
└── routing/labeled-requests.json  # 50 labeled requests for the router (T5)
```

## Scope

All agents in `agents/` move to Enact except the ones that stay local: `ampharos`,
`audino`, `braviary`, `castform`, `oracle`, `smeargle` and `sylveon`. These have no golden
file and are never a routing label.

| Group | Agents | Golden task kind |
| --- | --- | --- |
| Wave 1a | slowking, porygon, xatu, oranguru, machamp, metagross, abra | `report`, read-only |
| Wave 1b | mew, slowbro, arceus | `report`, read-only |
| Configurers | description starts with "X configurer." | `config-readback` |
| Builders | description starts with "X builder." | `pr` |
| Specialists | every other Enact-hosted agent | `report` or `pr`, per task |

Waves 1a and 1b come from the story. The other three groups are derived from each agent's
description by the runner. They are not waves the story defines. The runner reports routing
results per group.

## Golden task format

```json
{
  "agent": "uxie",
  "tasks": [{
    "id": "uxie-searchable-field",
    "message": "the request, as a person would send it",
    "repositories": ["owner/repo"],
    "expect": {
      "kind": "report | pr | config-readback",
      "must_include": ["fact or section", "re:<case-insensitive regex, checked automatically>"],
      "must_not": ["behavior that fails the task"],
      "tools_in_trace": ["Bash"],
      "forbids_repo_writes": true
    },
    "limits": { "max_cost_usd": 5, "max_minutes": 30 },
    "requires": ["secret-injection"]
  }]
}
```

- `report` answers in the result and writes nothing. `forbids_repo_writes` is `true`.
- `pr` opens a draft pull request titled `[enact-golden] ...` that passes the repository's
  own CI. It never pushes to the default branch and never merges. Every `pr` message also
  says: if the default branch already does this, open no PR and say where it is
  implemented. Before a wave's T3, check that each `pr` task's premise still holds on its
  repository and replace the stale ones. Close the golden PRs after review.
- `config-readback` writes configuration to the person's own dev/test stack through the
  product's HTTP API (`https://$PRISM_DOMAIN`, `PRISM_API_KEY`), with `X-Source-Repository`
  and `X-Source-Commit`, and reads it back through the same API. It never uses AWS
  credentials and never writes to soofi-safavi or production.
- `must_include` and `must_not` items starting with `re:` are checked automatically against
  the run's result. A reviewer checks the other items. `tools_in_trace` is checked in the
  run's Persist trace (thread for the run's `session_id`).
- `requires` names the T2 gates a task needs: `repositories`, `browser`, `secret-injection`
  (phase 3) or `remote-mcp` (phase 6). The runner skips a task whose gate is not open.

## Tests

| Test | What passes |
| --- | --- |
| **T1 Packaging** | Every Enact-hosted agent has a package under `enact/<agent>/` generated by `scripts/sync-enact-agents.mjs`. The package saves through `PUT /enact/agents/{name}` with `201 CREATED` or `200 UNCHANGED`, and a read-back is identical. A re-sync with no source change leaves the package unchanged. No stays-local agent is packaged. |
| **T2 Sandbox probes** | Now: a run can `git clone` an allowed repository and push a branch, run Node, and open a page with the browser tool. Run each probe on its own small run and keep the run ids. **Phase 3 gate:** a secret-injection probe. `PRISM_API_KEY` and `PRISM_DOMAIN` reach the sandbox, a product API call with them succeeds, and the value appears nowhere (see T6). **Phase 6 gate:** a remote-MCP probe. The sandbox reaches the `elephant` MCP server and lists its tools. |
| **T3 Golden tasks** | Each golden task whose gates are open runs **twice in a row** on Enact. Both runs end `SUCCEEDED`, pass every automatic check and stay within the task's `limits`. A reviewer accepts the other `must_include` and `must_not` items and the trace shows `tools_in_trace`. The median cost and time across the two runs must be within the task limits and the manifest's `max_cost_usd`. |
| **T4 Slowking benchmark** | Slowking on Enact scores the same submission as a recorded editor run. Every scorecard dimension must be within **5 points** of the reference. |
| **T5 Routing** | Arceus on Enact routes the 50 labeled requests in `routing/labeled-requests.json`. Pass: **at least 45 of 50** correct and **zero** routed to a stays-local agent. |
| **T6 No secret leaks** | No secret value (environment key, GitHub App token, Claude sign-in, partner credential) occurs in the run transcript, the run result, the Persist trace or the API, worker and sandbox logs. Check it for the T2 secret probe and every `config-readback` run. Search for the literal values, not only their names. Zero occurrences is the bar. |
| **T7 One MCP entry** | One `enact` MCP server entry (`https://<shared domain>/enact/mcp` with the `x-api-key` header) works unchanged in Claude Code, Cursor and Copilot. From each client, list agents, start a run, read it to the end and send a second message to the session. All three runs show in the ledger with channel `direct`. |

T1, T2, T6 and T7 are run by hand against the environment. Record their run ids and
results in the story. The runner below automates T3, T4 and T5.

## Runner

`scripts/run-enact-tests.mjs` needs Node 22 and nothing else.

```bash
# Validate the test files only. CI runs this. Without ENACT_URL or ENACT_API_KEY it is always a dry run.
node scripts/run-enact-tests.mjs --dry-run

# Run T3, T4 and T5 against an environment through its MCP endpoint
ENACT_URL=https://<shared domain> ENACT_API_KEY=<environment key> \
  node scripts/run-enact-tests.mjs --tests T3,T4,T5 --gates repositories,browser

# Narrow a run: one wave's agents, three at a time
node scripts/run-enact-tests.mjs --tests T3 --agent slowking,porygon,xatu --concurrency 3
```

The dry run checks the following:

- Every Enact-hosted agent has a golden file with 2-3 tasks.
- Each task's kind follows the rules: waves 1a and 1b use `report` and forbid repo writes,
  configurers use `config-readback` and builders use `pr`.
- IDs are unique and regexes compile.
- A Slowking T4 task is present.
- The routing file has exactly 50 requests, at least 8 near misses and no stays-local or
  unknown labels.

The runner calls `POST <ENACT_URL>/enact/mcp` (JSON-RPC, headers `x-api-key` and
`Accept: application/json, text/event-stream`). It calls `tools/call` `list_agents`, then
`start_run`, then polls `get_run` until `SUCCEEDED` or `FAILED`. It skips agents not yet on
Enact and tasks whose gates are closed. It writes `enact-test-results/<timestamp>.json`
(override with `--out`). The file holds per-run status, cost, duration, turns and checks,
and per-task medians against the task limits and the manifest's limit. It also holds
routing accuracy per group. The file never contains the key. It exits non-zero when a test
that ran fails.

## Recording the Slowking reference run (T4)

`golden/slowking.json` has two T4 tasks. `slowking-t4-roofing-crm` is recorded: Slowking in
Cursor scored Roofing CRM PR #22 at 59/100 (soofi-xyz/wow-website#191), and the first Enact run
scored 64/100 with every dimension within 5 points. `slowking-t4-oracle-property-intelligence` is
still a `TO_RECORD` placeholder. To record one:

1. Pick a real, already-submitted candidate assignment of the named type: a PR to the
   designated assignment repository, a hosted runtime, a demo, and the assignment-sent time.
   Fill `reference_run.inputs` (and `credentials_note` if the runtime needs a login; never
   put the credential itself in the file).
2. In the editor (Claude Code or Cursor with this plugin at the kit version you are
   testing), run the Slowking agent with the task's `message`, the `{{...}}` placeholders
   replaced by the inputs. Save the final evaluation Markdown outside the repo. It holds
   candidate data, so do not commit it.
3. Run `node scripts/run-enact-tests.mjs --record-reference <task-id> <evaluation.md> --editor "Claude Code"`.
   This parses the scorecard into `reference_run.scorecard`, `total` and `verdict`, sets
   `status: RECORDED` and stamps `recorded_at`. Set `kit_version` and `recorded_by` by hand.
4. Commit the updated `golden/slowking.json`. T4 then runs Slowking on Enact with the same
   inputs and compares each dimension's points. Record a new reference whenever Slowking's
   instructions or weights change.

The third Slowking task (`slowking-localhost-runtime-gate`) needs no reference. It is a T3
task whose answer is fixed: a local-only runtime is `0/100`, `Fail`.
