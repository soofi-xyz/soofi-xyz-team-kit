# Prism asset pipeline

## Paths
- `<pipeline>` is the directory that holds this `SKILL.md`. Resolve it from where you loaded this skill, never from the cwd.
- `<pipeline>/art-direction/system.json` is the visual system: grammar, color, lines, and the vocabulary mapping every keyword to a treatment. `art-direction/art-direction.md` holds the reasoning and composition rules. Tokens: `art-direction/tokens.json`. `art-direction/lexicon.json` is superseded history (each entry's `maps_to` points into `system.json`). Every `art-direction/...` path in the Prism skills means `<pipeline>/art-direction/...`.
- Scripts: `node <pipeline>/scripts/<name>.mjs`. Models: `<pipeline>/models.config.json`.
- Runs: `<runs>` is `$PRISM_RUNS_DIR`, default `~/.prism-assets/runs`. Relative paths passed to the scripts resolve against `<runs>`. Never write runs into the plugin tree.
- API keys: set them in the environment or in `$PRISM_ENV_FILE`, `~/.prism-assets/.env`, or `.env` at the plugin root (first match wins per key). `OPENAI_API_KEY` paints rays. `ANTHROPIC_API_KEY` is optional. If it is missing, use Claude in Cursor for ideation and do not run `ideate.mjs`. `GEMINI_API_KEY` is for raster fallback edits. `RECRAFT_API_KEY` is optional. Never print or commit a key.

Input: raw page or section copy. A section file is written only after an asset plan is approved.

Run directory: `<runs>/<page>/<YYYYMMDD-HHMM>/`.

## Phases
Design and painting are separate. Every phase reads the previous phase's JSON and writes its own; never carry a decision forward only in prose.

0. **System** (`system.json`). Read it first, every run, including `visual_slots`. When asked "what is the system?", return it (`definition_of_done`). A page outline is not in the system. Change it only through a proposal that is approved: write `<run>/system.proposals.json` (the word, 7 options generated, the top 3 shown as treatments that apply to any element, never as one-off pictures), then merge the pick into `system.json` with the date.
1. **Plan** (`asset_plan.json`) — take the section copy, the emphasis, and depiction. Show all three. Before `prism-asset-planner` and before any keyword mapping, apply `system.json` `visual_slots.suggestion` in order: the first matching rule wins. Suggest exactly one style per visual: background, focus, or distinguishing. Depiction does not choose the style. It chooses the subject: `user` is a circle the feeling happens to, `us` is a rounded square, `about_us` is the work or the system and may stay abstract. Then state the compositional layer separately (`single` or `flow`). Flow is not a style. A section may have more than one visual, each with its own style. Run the rule again on the new inputs. Do not skip it. Do not invent emphasis or depiction. Do not ignore a provided value. If emphasis or depiction is missing, stop and ask. Do not map article words to pick the picture. One background can still underlie the page: that is the background style used where a section's suggested style is background, not a second style invented per section. Then run `prism-asset-planner` for the remaining plan fields. STOP for approval.
2. **Read** (`<run>/<section>.reading.json`) — after the style and the compositional layer are suggested. Write the suggested style, its job, and the compositional layer. Do not map article words onto the copy to invent the picture. A feeling visual names only the vocabulary keys that carry the section feeling. An explanation visual names only the vocabulary keys that show the difference or the compositional flow it was assigned. Background is atmosphere only. A word with no entry goes to `unmapped`; if that visual needs it, return to phase 0 before composing. Suggested style `none`: skip the graphic. The page atmosphere skips to phase 4 with light only (`prism-light-layer`).
3. **Compose** (`<run>/<section>.composition.json`) — run `visual_slots.selection`. If the prompt does not state the subject or the feeling, stop and ask. Do not read a stored sentence to fill that in. Follow `motif_sourcing`. The copy does not choose the subject or replace the feeling. The situation has to hold what the copy is about. For the ranking, show situation names only. Do not describe the line, the subject, or the rays. Stop for the ranking. After one name is locked, search for photographs of that situation. Download several into the run's references folder and look at the pictures before writing the event. Use them to see the moment: where the subject is, what the path does, and what is in front of and behind the subject. Translate that moment into this kit. Do not copy an object the kit cannot build. Do not attach the photographs to the ray. Then write the event before any element, then illustrate that event and run `prism-prompt-writer` steps 2–3 once per visual. Do not paint before it is locked. A section with several visuals gets one composition per visual. Candidates serve that visual. A feeling visual carries the named feeling and adds no fact. An explanation visual shows only the difference or the compositional flow it was assigned. Compositional flow marks in one section stay the same size and the same weight. Each candidate uses exactly one transformation for that visual plus at most two relations, treatments, or states from the reading, and names them by vocabulary key. Candidates differ in composition, never by inventing marks. A blind critic scores each as text (`node <pipeline>/scripts/ideate.mjs --ideas`). Record the pick with: elements, vocabulary keys, hero ray pair and supporting rays, line color, type layout per breakpoint (`1536x1024`, `1024x1536`, recomposed not cropped), the type anchor, and the construction (the point the light starts from and the angles it shares). The ranking is the pick. Paint only after one motif is ranked.
4. **Paint** (`<run>/<id>.svg`, `<run>/<id>.png`) — before any pixels, check the picture against the suggested style, depiction, and the compositional layer. Do not replace them. Fail a focus visual that becomes a keyword diagram. Fail a feeling compositional flow mark that explains. Fail an explanation visual that only sets a mood. Fail `user` when the picture has no circle. Fail `us` when the picture has no rounded square. Fail `about_us` when a circle is standing in for the reader. Then render only what the composition names, as two artifacts. Rays: `gpt-image-2.5-sunburst` from `light_prompt` via `gen.mjs --reading`, light only. Geometry: exact SVG from `geometry`, per "Geometry" below. Measure the ray origin in the PNG and place an outline on that point, around the glow the ray leaves from. The outline is never flat-filled. Composite the SVG over the ray and rasterize at `size` for the read-back. Blurred SVG (`prism-light-layer`) is for the background library, not focus rays.
5. **Verify** (`<run>/readback.json`, `<run>/critique.md`) — `node <pipeline>/scripts/readback.mjs <run>/readings.json <id...>` (pass: blind ≥4, no missed bindings; max 2 revisions), then `prism-critique`, then `node <pipeline>/scripts/sheet.mjs <run>/readings.json <id-prefix>`. Show the sheet, the blind description, and scores. STOP.
6. **Export** — only after approval in this conversation, run `prism-export`.

## Geometry
- Strokes: 1.5 px at 1x with `vector-effect="non-scaling-stroke"` (`tokens.json` `geometry_line.weight`), `stroke-linecap="round"`, `stroke-linejoin="round"`.
- Line color: the graphic color of the ray that line meets, per `system.json` `lines.colors` and `shapes.graphic_colors` (blue/gold `#6CAE25`, blue/purple `#787AEE`, mint/blue `#64B8C7`, yellow/red `#F4480A`). The same darker color as the shape outline on that ray. Never the pale core, a ray fill, or a gradient on a line.
- Shapes: only the `system.json` grammar shapes, each with its one meaning; rounded corners except at a transition point into light. Size follows the composition. A shape may be large when that reads better. A shape large enough to read as an outline has no fill; its stroke is the graphic color of the ray it sits on (`shapes.graphic_colors`). A shape small enough to read as a dot is filled with that same graphic color. The line uses that same graphic color. When a shape sits on a line, the line stops at the shape's edge and continues on the other side. The line does not pass through the shape. A line enters from one edge of the frame and leaves through another. It does not begin or end in open ground.
- Hard edges are one flat solid color. Gradients are diffused light with soft edges. Never put a crisp edge around a gradient. No filters, blur, glow, or text in the geometry layer.
- The light starts on a vertex, edge, or center of the geometry and shares its angles; use the fan angles only when the geometry sets none.
- Sit on the 8 px grid. Scale per `system.json` `scale`: small players, light filling most of the frame, open ground only around the type. Nothing saturated, no line crossings, and no focal event behind the headline or CTA.
- Mobile: the idea reads top to bottom. Never end a vertical element in a symmetric downward cone of light; run the sequence diagonally or keep it horizontal and let the light leave at an angle.
- Give every labeled element an `id`. Labels are HTML, never baked into the graphic.

Log every correction in `<run>/critique.md` under `## Feedback`, then apply it to the skill, rule, or art-direction file that caused the miss.
