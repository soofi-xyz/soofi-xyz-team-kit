# Validation phases and gates

Run every promoted, schema-valid profile through these phases in order after generic intake reaches `CONTEXT_COMPLETE`. Intake is not a thirteenth phase and cannot use readiness verdicts. Use only `PASS`, `FAIL`, `BLOCKED`, and `APPROVAL_REQUIRED` during validation.

1. **Intake, terminology, and boundary** — resolve aliases, intent, direction, environment, datasets, adapters and consumers; classify every proposal as `CONFIGURATION` or `PRODUCT_CHANGE`. For every profile, use (or derive with recorded defaults) its `sourceWindowPolicy`, proactively compare recent complete UTC-day PROD metadata read-only, and ask the user to confirm the recommended day or a permitted longer range. Gate: no ambiguous term remains, every unresolved product change has a named handoff, and no source window proceeds without explicit confirmation; in the final run the window is `CONFIRMED`.
2. **Repository and environment discovery** — resolve the profile's repository plan in order: requested ref, one matching open PR when allowed, then default branch. Reuse a local checkout only when its remote and HEAD exactly match the remotely selected SHA. Pin the selected candidates and discover configured account, region and resources. Gate: every required path exists at one unambiguous commit SHA, every rejected candidate is recorded and discovery is read-only.
3. **Safety and access preflight** — classify sensitivity, verify permissions without reading secrets, set cost/scan bounds and environment write policy. Confirm that the PROD-derived window covers at least the profile minimum, preserves every required source family/join and remains read-only until a separate DEV staging approval; in the final run, every staging upload of the window carries its own approval digest. Gate: no prohibited access, partial/random sample or unbounded operation is required.
4. **Evidence registry** — assign stable evidence IDs and observation times. Gate: every planned claim has an admissible, sanitized evidence source; in the final run every input binding lies under the confirmed window's manifested DEV prefix or the run's own output root.
5. **Language and dataset model** — validate language definitions, required/optional fields, types and dataset roles. Gate: the Lexicon definitions are immutable and compatible; omitted optional JSON fields materialize as null.
6. **Configuration and directional mapping** — resolve every required profile direction by its exact mapping ID, version, source paths and artifact path; validate languages, inputs, expected outputs, fields, schema shape, formats, normalization, expressions, options, SQL digests and graph bindings. Gate: every required direction resolves from the pinned configuration repository with no unsupported option, implicit inverse, ambiguity, undeclared schema, or product-boundary concern disguised as configuration.
7. **Test coordination and Spark proof** — run every declared repository test, verify the pinned sanitized fixture manifest, assemble expected-output/negative cases and oracles, then execute every required directional mapping using the deployed major/minor compatibility target. Generic typecheck, lint, synthesis or unit-test success is supporting evidence only. Non-deterministic profiles additionally require confidence, thresholds and human-review evidence. Gate: each direction has mapping-specific expected and negative evidence without Silvally claiming Test ownership.
8. **Release and deployment provenance** — verify Deploy-owned environment records and bind the active deployment to immutable source/configuration digests. Gate: no deployment drift or latest-PR-wins race remains; Silvally performs no deployment.
9. **Transform runtime proof** — verify an approved DEV or existing immutable execution, committed metadata, schemas, physical counts/hashes and cost. Gate: status, manifest and physical artifacts reconcile, and every execution has its own recorded approval.
10. **Persist canary and graph closure** — when required, coordinate a bounded canary through Persist's documented surface, prove unique stable IDs and endpoint membership, then consume receipt/readback evidence. When the profile sets `persistPolicy: forbidden`, do not invoke Persist; prove graph closure directly from committed Transform outputs and record the canary as not required. Gate: zero dangling endpoints and pinned compatibility for every dependency actually used; placement, retention and custody remain Persist-owned.
11. **Export, hydration and round-trip parity** — verify exporter timezone/window semantics, immutable manifests, artifact hydration and declared forward/reverse parity. Gate: counts/hashes/order and required fields reconcile after normalization.
12. **Final PROD-derived validation, package, handoff and readiness verdict** — confirm that phases 1–11 passed in `observed-dev` on the confirmed PROD-derived window, record `finalValidation`, validate the reusable configuration/readiness package, reconcile report statuses, route product changes and compute `READY`, `NOT_READY`, or `BLOCKED`. Gate: the final PROD-derived validation passed (otherwise `BLOCKED` with `FinalProdDerivedValidationRequired`), package and report agree, contain no protected data, and state Marketplace-registration metadata without claiming Marketplace or Deploy ownership.

## Final PROD-derived validation

A run reaches `READY` only through a final pass of phases 1–12 in `observed-dev` against a user-confirmed PROD-derived source window:

- phase 1: `sourceWindowSelection.status` is `CONFIRMED` for a whole-UTC-day window of at least `minimumCompleteUtcDays`, every day of it compared and complete;
- phase 3: each DEV staging copy of that window was uploaded under its own approval digest, with a matching manifest readback;
- phase 4: every input binding lies under the confirmed window's staging prefix (or a previous step's output under the run's output root);
- phases 9–11: every approved DEV execution reconciles physically and passes closure, parity and regression gates;
- phase 12: `finalValidation.status` is `PASS`.

`synthetic-local`, `bounded-dev-dry-run` and synthetic or edge-case DEV runs are earlier phases. They prove shape, negatives and wiring and are reported as `modeScopedResult`, but phase 12 stays `BLOCKED` and the verdict is never `READY`. Missing PROD metadata access, a missing confirmation, or a missing staging or execution approval is `BLOCKED` with a handoff naming what is needed.

## Approval placement

Finish read-only work first. Immediately before each DEV external write, create an operation-specific approval record and stop at `APPROVAL_REQUIRED`. After matching explicit approval, perform only that operation. Any changed target, payload, digest, cost ceiling or retry requires a new approval.

`synthetic-local` and `bounded-dev-dry-run` never cross a DEV write gate. PROD never crosses one in any mode.
